tny ask -B — fire a turn, get an ID, walk away

Dotted-underlined things have tooltips — hover or tab to them.

One sentence: -B runs the identical ask turn and defers its output into the session instead of stdout. Nothing else changes — same backends, same permissions, same session commands. 
# foreground
tny ask --json "review this" \
  > answer.json
≡
# background
id=$(tny ask -B "review this")
tny session $id --json | jq .result

until your shell is free and the ID is printed

a plain detached child — no tmux, no daemon

the ID is a session — every existing command works

Is it tmux? No.

tmux keeps a live terminal you re-attach to. -B keeps a result you read from disk.

tmux sessiontny ask -B
What runs a shell inside a pty, under a tmux server one forked tny child, setsid-detached, no terminal at all
How you "look at it" re-attach to a live screen read files: tny session <id> shows status, live partials, then the result; task.log has the streaming tool trace
Interacting mid-run type into it stop it, or take over: --resume --steer interrupts & redirects
When it ends session lingers until killed child exits on its own; the session keeps status: done + the full result forever

Three artifacts, one job each

The design separates truth, control, and record — so no artifact ever has to lie.

truth
lock

Is a turn running right now? The kernel answers — self-releasing on any death, no stale-lock cleanup, ever.

control
pid

Where to send stop. Group-signalled, so spawned hosts die with the child — no orphans by construction.

record
session.json

What happened — durable. Status, exit code, and the result object that is the answer.

Where it lives on disk

~/.tny/sessions/<ws-hash>/3f9a1c2e77b04d58/
├── session.json  ← status, result, transcript
├── task.log      ← live stream + tool trace
├── pid           ← stop target
└── lock          ← one writer, kernel-enforced

Session states

⏵ running → ✓ done / ✗ error / ⏸ interrupted ⤷ ⚠ stale

"stale" is computed by readers from status ⨯ lock probe — a crashed child can't update its own status, but it can't keep holding a kernel lock either. The disagreement is the detection.

The agent playbook

What a script or another agent driving the tny CLI does — and exactly what it gets back.

# 1 · launch — returns in ~10 ms
id=$(tny ask -B "audit the Makefile for missing deps")

# 2 · poll until finished
tny session $id --json | jq -r .status        # running → done

# 3 · read the answer (works for codex/cursor too) — or watch live
tny session $id --json | jq .result
tail -f ~/.tny/sessions/*/$id/task.log

# 4 · hung or no longer needed? end it cleanly
tny session stop $id                          # SIGTERM the group → interrupted

# 5 · changed your mind mid-run? interrupt & redirect (re-detach with -B)
tny ask -B --resume $id --steer "drop that — check the tests instead"

# 6 · continue the conversation (after it ends)
tny ask --resume $id "now fix what you found"

Guarantees an agent can rely on

The ID never races the disk printed only after session.json exists with status:"running" — tny session $id works the instant the shell returns
The result is the foreground output result ≡ what ask --json would have printed — captured at the event layer, so it holds for codex/cursor/ACP whose transcripts store only a resume pointer
Liveness cannot be fooled truth is a kernel flock, not a pid: self-releases on any death, immune to PID reuse, zero cleanup code
Every ending is recorded all exit paths finalize status + exit_code + result; the one uncatchable case (kill -9) is still detectable as stale, and stop --kill even closes that gap by writing the status itself
No orphans, no hijacks hosts the child spawned share its process group and die with it on stop; hosts it merely attached to are never killed; the child never registers itself as an attach target for foreground tny
Never wedges on approvals same as foreground ask: yolo approves, ask-mode denies — a background task can end badly, but can't wait on a human
Fine print & known limits
  • Parent exit code covers the launch only. $? is 0 once the child is off; the turn's outcome lives exclusively in status/result.exit_code. Scripts must poll, not trust $?.
  • flock is advisory and unreliable on some network filesystems (NFS home dirs). Local ~/.tny is the supported case.
  • The lock work also fixes a latent bug: two concurrent ask --resume on one session can corrupt it today; the retrofit closes that for foreground and TUI paths too.
  • No --timeout in v1 — a hung turn holds running honestly (live pid, held lock); stop is the remedy. A watchdog flag is a natural v1.1.
  • --steer abandons pending tool calls by design. It is interrupt-and-redirect, not a live steer. Its fidelity is fixture-tested per backend — notably a spawned codex host dies with the group, so the steered resume rides on the host pointer plus codex's own on-disk session.
  • wasm / browser build: no fork(2) — -B fails immediately with a clean error, enforced in wasm CI (ADR-0017 parity).
  • --ephemeral is rejected (nothing on disk for the id to point at). --resume -B composes — background a follow-up turn; the pre-fork lock serializes it.
  • Recycled-pgid guard: stop signals only while the lock probe confirms a live holder — it will not fire signals at a pid that has been reused.
