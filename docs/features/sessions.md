# Sessions

Every supported provider uses the native session transcript and detached runner lifecycle.

## Identity

Session ids are generated by tny, opaque, unique per workspace. List is workspace-scoped by default (`--all` for every workspace). Pagination: `--limit 1-100`, `--cursor`.

## On disk

```text
~/.tny/sessions/<workspace-hash>/<id>/
  session.json      # metadata, messages, tool steps (redacted)
  results/          # large tool-result blobs, referenced by handle
  recovery.json     # partial assistant text + last event offset
  lock              # flock target: writer ownership, even between turns
  pid               # session runner's pid — signal target for `session stop`
  task.log          # runner's stderr/stdout (progress, tool lines)
  sock              # live runner's AF_UNIX socket (docs/adr/0053) — the
                    # attach point; gone when no runner is alive. Homes too
                    # deep for sun_path fall back to $TMPDIR/tny-<uid>/<id>.sock
```

`session.json` never stores API keys or MCP header values. Tool results larger than `max_tool_result_bytes` live in `results/` with a handle the model reads via `read_tool_result`.

All `session.json` writes are atomic (write + rename), so readers never
lock — they always see a complete document.

A terminal `status` records turn completion while the runner may still be
finishing shutdown. The runner retains its writer lock through its last save,
log flush and socket removal, then releases it before sending `bye`
([ADR 0104](../adr/0104-runner-quiescence-ownership.md)). A resume requires the
writer to be free and reloads the saved conversation under that ownership.
Serve runners retain ownership between turns, including rejected turns.

## Background conversation turns

`tny agents` lists saved sessions marked `background:true`, including explicit
`ask -B` and Left-arrow handoffs, plus live sessions. The writer lock determines
liveness; a stored running state with no writer is stale. Completed/error/interrupted
rows remain selectable after the runner exits.

Enter attaches when a live runner accepts the unique owner handshake. This retains
the same active turn, permission mode, pending decision, model and workspace
without reposting a prompt. Otherwise it opens a clearly labeled **saved read-only
transcript** with continuation guidance. A rival owner, held lock or unreachable
runner cannot hide saved text. Completed/unlocked rows also open read-only.
Inspection does not resolve providers, refresh credentials, start runners,
activate checkpoints, or save session/settings/auth stores; it works without
usable provider configuration.

### Explicit continuation and ownership

Submitting a prompt from a view without a saved checkpoint requests
continuation of the selected session, preserving its ID and history. `/continue`
in a background view acquires or attaches that same session, never an unrelated
`last` session. A held writer lock permits only an owner-handshake attempt. If
another owner is attached or the runner is unreachable, execution is refused:
no new writer, socket replacement or session persistence. The read-only view stays
usable and continuation can be retried when ownership becomes available.

Starting a new runner requires acquiring the writer lock and reloading the latest
saved conversation under that lock before execution. Provider/model/workspace
selection and saved task reconciliation use that fresh session. Resolution failure
does not turn inspection into a writer. ADR 0104's teardown barrier is unchanged:
`done` and `turn_end` describe the turn, not permission to acquire or steal the
writer; the old runner retains ownership through shutdown, final save and socket
removal. No force takeover is introduced.

New execution uses the selected session's saved provider, model and workspace,
with current settings and launch flags for remaining options. Legacy missing
metadata uses the existing fallbacks: missing provider selects `openai`, missing
model uses the selected provider's current default, and missing workspace keeps
the current workspace. These fallbacks do not reconstruct historical permissions,
effort, credentials, SSH configuration or other options never stored. Live
attachment instead uses the existing runner's effective configuration. No
historical configuration persistence is added.

Saved read-only views allow only `/help`, `/clear`, `/transcript`, `/copy`, `/trace`,
`/agents`, `/quit`, `/exit` and `/continue`; `/cancel` requires a live attachment.
`/clear` clears the display, not the saved session. All other commands, including
`/new`, `/reset`, `/resume`, `/rename`, `/compact`, settings/provider switches and
auth commands, are blocked. Attached background replicas also block direct
mutations: prompts, steering, permission replies and cancellation go through the
owner channel. Read-only and save guards are distinct from the background
detach-on-exit flag; neither an attached replica nor an unowned saved view may
write back its local copy on exit.

Dashboard/view exit detaches background work. `/agents` or Ctrl-X returns to the
list without restarting it. Explicit cancellation of an attached turn remains
bounded; an unowned read-only view cannot cancel another writer. Ordinary
foreground quit/interrupt behavior is unchanged. New-runner continuation from
these views is rejected before mutation in wasm and in-process modes, including
`TNY_ISOLATE=0` and macOS post-TLS containment; there is no unlocked in-process
fallback. A successful live attachment remains usable where supported even when
starting a replacement runner is unavailable. Ephemeral mode cannot import saved
sessions. See [ADR 0154](../adr/0154-agents-session-inspection-and-continuation.md).

### Handoff checkpoints and recovery

A Left handoff saves a `continuation` object in the atomic session document,
after a completed tool result and before the next call or POST. It records
pending calls, consumed index and native/runtime continuation state. A fresh
executable inherits the continuous writer lock and existing listener. Resolved
configuration, credentials and provider affinity travel only through anonymous
IPC; no secret configuration checkpoint is written. Failures before activation
retain/recover foreground work or report the saved checkpoint honestly. A
completed turn removes its continuation checkpoint. This is controlled handoff,
not a guarantee of automatic recovery from arbitrary external-effect crashes.
See [ADR 0107](../adr/0107-tool-boundary-restart-and-agents-dashboard.md).

`tny agents --json` distinguishes `running` (active work) from `live` (held writer,
including an idle completed runner). A done row remains done while that writer
waits for another prompt. `/agents` or Ctrl-X detaches back to the list; observer
clients reconnect after exec. The transferred owner connection stays continuous.

If a restart exits before activating pending work, dashboard selection only
inspects the saved continuation. A typed prompt is refused while a saved
checkpoint is present, including consumed or invalid checkpoints: it is **not
submitted or queued**. **Use `/continue` in that background view to validate the
checkpoint through existing recovery.** Consumed or invalid work is rejected.
Recovering valid unconsumed work resumes the retained turn without a new user
message and may release retained tool calls and other effects. CLI
`tny resume ID` remains an explicit recovery entry point; its behavior is unchanged.
Outside a background view, `/continue` still resumes the latest workspace session.

Use the original provider configuration: recovery checks endpoint/settings/repository
identity, restores saved effective options and re-resolves credentials normally.
A configuration mismatch, wider permissions/tool access, unsupported mode or
already-consumed or invalid checkpoint is refused before pending effects. The
sole writer atomically marks a validated checkpoint consumed before releasing
those effects; ordinary missing-result repair cannot discard or replay its pending
batch. These exactly-once protections cover the controlled handoff/recovery
protocol, not
unknowable external effects after arbitrary crashes or automatic reboot execution.
See [ADR 0108](../adr/0108-checkpoint-recovery-and-hosted-tool-boundaries.md), whose
dashboard activation rule is amended by [ADR 0154](../adr/0154-agents-session-inspection-and-continuation.md).

## Durable jobs ([ADR 0093](../adr/0093-durable-native-jobs-and-verified-retry.md))

A durable job is a separate record under `~/.tny/jobs/<32 hex id>/`, not a
session field: `job.json` (0600) under `state.lock`, an `owner.lock` the live
supervisor holds, immutable `attempt-<n>.json` snapshots and one bounded
`item-<n>.log` per item. Each ask item still *creates an ordinary session* —
the supervisor runs `tny ask --events=jsonl`, so the session, its transcript
and `tny resume` behave exactly as for any other turn, and the item records
that session id plus the hashes a later retry re-verifies. Cancelling or
removing a job never touches those sessions. A job whose supervisor is gone
reads as `interrupted` with `cleanup:"unknown"` — the same honesty a stored
`running` status without a live lock holder gets here. See
[jobs.md](../jobs.md).

## Process isolation ([ADR 0053](../adr/0053-forked-turn-isolation.md))

On native builds **every turn — foreground `ask`, TUI, and `-B` — runs in
a detached session-runner process** (fork + `setsid`, no tmux). The
calling process is a thin renderer over `<dir>/sock`. A crash or SIGKILL
leaves the runner finishing the turn into `status`/`exit_code`/`result`.
Explicit Ctrl-C, TUI Ctrl-D/quit/EOF, and foreground SIGHUP/SIGTERM stop
the run. A second Ctrl-C forces termination; cancellation also escalates
after five seconds ([ADR 0081](../adr/0081-reliable-session-interruption.md)).
`tny resume` then continues the conversation, and `tny session attach
<id>` streams a live run (snapshot, then events; ^C detaches, `tny
session stop` cancels). The TUI's serve runner also owns the provider
host and MCP servers across turns. Forced termination on macOS/Linux also
enumerates descendants to kill the separate groups created by tools and hosts.

To stop a run from another terminal, use `tny sessions` to find its id,
then `tny session stop <id> --kill`. The command first requests graceful
cancellation, then kills an unresponsive runner, verifies writer-lock release,
and records `interrupted`/137. Crash survival and explicit `ask -B` background
runs remain available; an observer's `session attach` Ctrl-C still detaches.

In-process turns remain deliberate outside the runner-owned CLI/TUI path:
wasm (no `fork`), `--ephemeral` (nothing durable to survive for, [ADR
0020](../adr/0020-ephemeral-sessions.md)), the `TNY_ISOLATE=0` debug escape
hatch, `tny ask --events=jsonl` (the canonical foreground event stream is
this process's own engine, [ADR
0090](../adr/0090-canonical-foreground-ask-events.md)), mode, and libtny embedders. On macOS, a caller that
has already initialized SecureTransport also keeps later turns in-process;
that fork-safety containment is separate from the deep-path socket fallback
above. These in-process modes have no runner socket.

Without that runner there is no control pump behind a synchronous tool, so
the turn's cancellation signal is what a blocking tool consults directly. An
interrupted `terminal` command is stopped along with the descendants it
started — including ones in their own process group or session — and reaped;
unrelated processes are never touched, and a `background: true` command stays
detached by design. The tool reports `exit code: 130` and the turn ends
`interrupted`.

## Session control channel ([ADR 0058](../adr/0058-session-control-channel-roles-and-tool-ops.md))

Each socket client must first declare exactly one role:

- `owner` — the unique frontend that may start, steer, cancel, end, answer
  permissions, and answer free-text questions;
- `observer` — an attach client that receives snapshots/events but may only
  detach;
- `tool` — a short-lived child that may only request `ask_user` or
  `image_attach`.

The TUI owner's hello includes `"can_answer_questions":true`. A
non-interactive `tny ask` owner omits it, so `ask_user_question` returns its
fallback immediately instead of waiting on stdin.

Tool requests carry bounded string correlation ids. `ask_user` is forwarded
only to the owner; an observer cannot answer, and owner disconnect fails a
pending question closed. `image_attach` accepts only paths under the existing
allowed roots and png/jpeg/gif/webp files detected by magic bytes. Its success
ack is sent only after the image enters ADR 0008's pending-image queue, so it
becomes user-role content on the next native provider request.

While a `terminal` child is running, the terminal wait performs a bounded pump
of these control requests and their owner replies only. It never re-enters
backend dispatch. Local terminal children receive the runner's actual socket
path in `TNY_SESSION_SOCK` — including the deep-path fallback shown above — and
the current id in `TNY_SESSION_ID`.

The subprocess verbs are unavailable without that environment/socket. This
includes wasm and the deliberate in-process modes above: they print
`tny: no session socket (set TNY_SESSION_SOCK or run inside tny)` as one stderr
line, exit 1, and never read `/dev/tty`.

## Runtime status ([ADR 0031](../adr/0031-background-ask.md))

Detached and isolated turns add three top-level fields to
`session.json` (since [ADR 0053](../adr/0053-forked-turn-isolation.md)
every completed turn records them, not just `-B`):

- `status` — `running | done | error | interrupted`
- `exit_code` — int, present once the turn finished
- `result` — object: the exact JSON foreground `tny ask --json` would have
  printed for this turn. Read it with `tny session <id> --json`.

Old sessions simply lack all three; readers treat absence as "not a
background task". A foreground `--events=jsonl` turn records the same fields
on a session that carries them, and records them honestly: if the stream to
stdout failed, the stored `status`/`exit_code` say so while `result.output`
still holds the provider text the turn really produced.

The pid lives in the separate `<dir>/pid` file (the
control channel for `tny session stop`), not in the document — the
background child stays the sole writer of `session.json`.

### Lifecycle

```text
running ──► done          # turn finished; exit_code + result stored
        ──► error         # connect/engine failure; reason recorded
        ──► interrupted   # stopped (`session stop`, steer takeover, signal)
```

`tny session <id> --wait [--timeout SECS]` blocks on the same lock probe
until the turn finalizes and exits with the stored `exit_code` (124 on
timeout; [ADR 0041](../adr/0041-session-wait.md)).

**Stale** is derived, never stored: `status:"running"` while the `lock`
flock is *free* means the writer crashed. Liveness is the lock probe (a
non-blocking shared flock attempt), not `kill(pid,0)` — immune to PID
reuse, and `flock`'s self-release on crash means no stale-lock cleanup
exists, ever. `tny session <id>` reports `running (pid N)` or
`running (stale — process gone)` accordingly, prints the transcript and the
checkpointed partial text of a live run (so a backgrounded turn is readable
while it streams — rerun to poll), and only advertises
`--continue-recovery` for runs that are no longer live. A `running` session
with no `pid` file yet is "starting" (a milliseconds-wide window between
fork and the child's first writes).

### Single-writer lock

The exclusive `flock` on `<dir>/lock` is held for the duration of a turn by
**every** turn-running writer — the background child (acquired before the
fork, inherited across it), foreground `ask --resume`, and TUI resume. This
is a retrofit: before ADR 0031 nothing locked, and two concurrent resumes
could corrupt a session. Bare `--resume` on a held lock now fails with
`session <id> is still running (pid N)`; `--steer` is the explicit takeover
path (see [cli.md](../cli.md#background-one-shots-tny-ask--b)). Known
limit: flock is advisory and unreliable on some network filesystems.

## Ephemeral mode

Use the leading global flag on the TUI or CLI:

```bash
tny --ephemeral
tny --ephemeral ask "review this workspace"
```

`tny ask --ephemeral` is also accepted, and `--no-save` remains an alias.
The conversation remains multi-turn in memory until the process exits, but tny
does not create or update:

- `session.json`;
- `recovery.json`;
- `results/<handle>.txt` (large results use a process-local memory store);
- `~/.tny/history` (TUI history is process-local);
- child-agent session records (native subagents inherit `--ephemeral`);
- `~/.tny/memories.json` through `memory set`.

Saved-session operations are intentionally incompatible with ephemeral mode:
`resume`, `--resume`, `-r`, `-c`, `/resume`, recovery, migration, and import do
not load stored conversation state. Native subagents are one-shot, so their
`message`, `inspect` and `lifecycle` actions are unavailable. Existing user memories may
still be read. `tny ask --json` returns `"ephemeral":true` and an empty
`session_id`.

The local guarantee does not invent retention controls for provider protocols.
Codex starts its host thread with `ephemeral:true`; the native OpenAI Responses
wire sends `store:false`; other host agents may retain request data according
to their own policy. Ephemeral mode is not a filesystem sandbox: ordinary
workspace-changing tools still work when permitted. See
[ADR 0020](../adr/0020-ephemeral-sessions.md).


## Skill injections

A user message that mentioned a skill ([ADR 0056](../adr/0056-skill-mention-injection.md)) is stored as the model saw it: the `<skill>` block, then the typed text. A top-level `skill_injections` array, one `{ "message": <index>, "skills": [...], "display": "<typed text>" }` per such message, lets transcript views show the typed text and stops a repeat mention from re-sending a body that is still in the verbatim window. Host sessions record it too (with no messages) so the reminder logic is the same. Old sessions simply lack the array.

## Compaction (native)

After **eight** completed turns, keep the latest **four** verbatim and replace older turns with a structured summary (requests, outcomes, files, commands, interruptions). `/compact` forces condensation of everything before the latest turn. The on-disk transcript stays intact; only the model view shrinks.

## Recovery

Persist streaming text and tool progress continuously. `tny ask --resume last
--continue-recovery` replays partial output from `recovery.json`. Outside a
background view, `/continue` retains its latest-workspace-session behavior. In a
background view it acquires/attaches the selected session and explicitly recovers
an unconsumed handoff checkpoint as described above; opening the view alone does
not activate it, and a refused prompt is never queued for recovery.
`tny session recover <id>` copies a corrupt session. `tny doctor` prints the recover
command when it can fix a file.

Recovery is disabled in ephemeral mode because no checkpoint is written or
loaded.

## Isolation

Additional directories do not create sessions or history. Primary workspace owns the session key.
