## Spec (from issue #99, ADR 0057 decision 5, ADR 0058, ADR 0064)
When tny IS the harness, a first-party `tny` verb issued inside the `terminal` tool must not run as a nested process that has no permission engine, no session grants, no undo record, no warmed MCP client, and no `--ssh` context. Read first: docs/adr/0057, 0058, 0060, 0064; src/core/tools_shell.c (tool_shell_execute, shell_control_env, control_pump), src/core/tools.c (tools_call_prepare / permission identities / tools_queue_image), src/core/tools_fs.c (t_edit_file, undo_record ~97-120), src/core/edit.c/.h, src/core/tools_ssh.c (remote edit ~264-330, terminal ~539-613), src/core/tools_ext.c (memory, skill, subagent ~136-180 and the child-mode rule ~169, ask_user_question), src/mcp/mcp.c (mcp_call_tool, mcp_call_cli), src/core/perm.c, src/core/runner.c, src/core/config.c (mode resolution), docs/features/permissions.md.
Design:
- Recognise a SINGLE SIMPLE COMMAND whose argv0 is `tny` (or an absolute/relative path ending in `/tny`): tokenise with POSIX-shell quoting rules (single quotes, double quotes, backslash escapes; you may share a tokenizer with the permission work if one exists in src/core/perm.c on this branch, otherwise write a small one in src/core/shellwords.c with unit tests). If the command contains any of `; | & && || $( ` < > >>`, a newline, a here-doc, or an env-assignment prefix, it is NOT intercepted and goes to /bin/sh unchanged. EXCEPTION that must work because it is the documented way to pass payloads: `tny edit FILE <<'EOF' ... EOF`, `tny edit --json FILE <<'EOF' ... EOF`, and `printf ... | tny edit FILE` / `echo ... | tny mcp call S/T`. Handle these two shapes explicitly: a here-doc whose body becomes stdin, and a single left-hand `printf`/`echo`/`cat FILE` producer piped into a tny verb. Anything more complex is not intercepted (document the boundary; the standalone binary still works, it just runs cold).
- Intercepted verbs and their in-process routes:
  - `tny edit [--json] [--marker M] FILE` → the shared tny_edit_file_exact with the same permission identity and path canonicalisation as the `edit_file` tool (write category, `perm_path_allowed`), the undo hook recorded so `/undo` keeps working, and the CLI's exact stdout/stderr/exit-code contract reproduced in the tool result (`exit: N` line + the CLI's output), so the model sees exactly what the standalone CLI prints.
  - `tny mcp call SERVER/TOOL` → the warmed in-process MCP client (mcp_call_tool via the tools_env) with identity `mcp:server/tool`; never spawn a second server.
  - `tny memory ...`, `tny skill show NAME` → the existing in-process tool functions (`memory`, `skill`), same permissions.
  - `tny image attach PATH`, `tny ask-user ...` → in-process via tools_queue_image and the engine's frontend ask hook (ADR 0058), bypassing the socket round trip; behaviour and output identical to the CLI. Keep the socket path working for scripts that call tny from deeper nesting.
  - `tny ask ...` without `-B` → refused with a one-line tool error explaining that foreground nested agents are not allowed inside a turn and to use `tny ask -B` + `tny session ID --wait --json`. With `-B` → not intercepted (runs as a real child) but the child inherits the parent's permission mode and cannot widen it: export `TNY_NESTED=1` (plus the effective mode) from the terminal child env, and make config mode resolution in src/core/config.c refuse a wider `--permission-mode`/`TNY_PERMISSION_MODE` when nested (clean error, exit 1). Add a test.
- `--ssh` (ADR 0022): the remote shell has no tny. When ctx->ssh_host is set, an intercepted `tny edit` routes through the ssh-aware implementation in tools_ssh.c (cat, local replace with tny_edit semantics, content on stdin to a temp file, atomic mv); other intercepted verbs stay local as today. A non-intercepted command still runs remotely unchanged. Never emit `ssh host tny ...`.
- Events: tool_start/tool_end for an intercepted call carry the verb and target as `detail` (e.g. `tny edit docs/x.md`, `mcp:server/tool`) so Python extensions and ACP clients keyed on tool name still see a meaningful name, not an opaque `sh -c` blob. Permission prompts show the same detail.
- Profiles: the intercept is active in every tool profile (the `tools` setting from issue #100 may or may not be merged when you start; do not depend on it).
Tests: unit tests for the tokenizer and the intercept decision table (intercepted / not intercepted / refused) including the here-doc and pipe producer shapes; permission verdicts for intercepted verbs identical to the typed tools (tests/test_perm.c or a new tests/test_intercept.c); an MCP test proving no second spawn (tests/test_mcp.c fake server); an `--ssh` integration case editing a remote file via the intercept (tests/integration/test_ssh.py); the nested-mode refusal test; `/undo` after an intercepted edit; an integration test through mock_openai.py where the model runs `tny edit` inside terminal and the next request shows the edited file. Mutation TARGETS. `make leaks` on the new paths.
Docs: docs/features/mcp-and-skills.md (intercept table: verb → route → permission identity), docs/cli.md (a short "inside tny" note on each verb), docs/features/permissions.md (TNY_NESTED rule), ADR 0063 "in-process intercept of first-party verbs" (state wasm: not applicable, terminal is the clean error there).
